图中的「单一 TEE」指一套可配置、可审计的统一验证程序，而非单个物理服务器。评级属于技术研究判断，不是声称这些数据在全球都已开放、统一或可无许可访问。

02简化证明输出Illustrative TradeEventProof

// ILLUSTRATIVE — NOT AUDITED. 示意结构，非可部署合约
struct TradeEventProof {
    bytes32 orderCommitment;          // 订单承诺
    bytes32 milestoneId;              // 里程碑
    bytes32 trustedSourceId;          // 可信数据源
    bytes32 sourceRecordCommitment;   // 源记录承诺
    bytes32 eventType;                // 事件类型
    bytes32 policyHash;               // 规则版本
    bytes32 verifierVersion;          // 验证器版本
    uint256 expiry;                   // 过期时间
    bytes32 nullifier;                // 防重放标识
}

这只是示意数据结构。实际合约还需要链 ID、合约域隔离、签名者授权、数据签发时间、撤销策略、验证器密钥轮换等保护。对应文件：contracts/TradeEventProof.sol（仅用于说明）。

字段组回答的问题缺失时的风险
orderCommitment / milestoneId这条证明绑定到哪笔订单、哪个里程碑？跨订单复用证明
trustedSourceId / sourceRecordCommitment数据来自谁、原始记录是哪一条？来源不可核验
eventType / policyHash / verifierVersion按哪一版规则、哪个程序判定的？规则变更无法追溯
expiry / nullifier证明是否过期、结算授权是否已被用过？重放与重复放款

03链上可以检查的约束Onchain-checkable constraints

  1. 来源在该订单的认可数据源集合内；
  2. 订单、货物 / 集装箱和事件存在受信任的绑定；
  3. 事件是实际发生状态而不是计划状态；
  4. 事件时间满足合同约束；
  5. 证明绑定到正确的合约、链、订单和里程碑；
  6. 证明未过期、未撤销，且结算授权未被重复使用。

04安全重点Security emphasis

TEE 处理过 API 响应，不代表 API 响应没有被伪造。TLS 终端认证、数据源签名、会话安全和输入来源证明必须纳入威胁模型。ZKP 也不能自动弥补错误的原始数据。
An attested execution environment does not authenticate its inputs.

05实现补充What an implementation must add

除上表九字段外，实际系统还需要处理：链 ID 与合约域隔离、签名者授权与轮换、数据签发时间、撤销策略、争议冻结与仲裁、部分里程碑放款、外部事件更正或撤销、资金不足与重复执行、失效证明与权限变更。详见 场景与多里程碑协议。

Peer 式设计中「资金托管与证明验证分离」是最值得参考的模块化思想；但贸易 Escrow 需要新增分期放款、可信货物 / 单据绑定、长周期争议与法律责任安排。
