可验证贸易履约事件协议

Verifiable Trade Event Protocol
将可信第三方产生的标准化贸易事件，转换成可验证的付款条件。

不是让 AI 自动判定货物质量，而是把国际贸易中已经标准化、由船公司、银行、eBL 平台产生的数字事件，变成资金托管合约可核验的放款条件。

Not "AI judges cargo quality" — standardized third-party trade events become verifiable conditions for programmable escrow.

读白皮书 Whitepaper → 技术架构 Architecture

01 · 核心判断The core judgement

最值得优先验证的，不是让 AI 自动判定货物质量，而是将国际贸易中已经标准化、由可信第三方产生的数字事件转化为自动放款条件。 建议从 DCSA Track & Trace → TEE 验证 → USDC Escrow 切入，逐步扩展到电子提单与单据相符付款。
Start from trusted carrier events, not from automated quality judgement.

国际贸易存在大量标准化业务记录，但数据分散在船公司、银行、海关、港口和电子单据平台中。Peer（原 ZKP2P）的核心思路是对链下支付事实生成可验证证明，再触发链上资金托管合约结算；把这一模式迁移到国际贸易，就得到下面的三层结构。

02 · 三层架构Three layers: facts / proof / settlement

① 事实层 Facts
Read trusted sources

读取可信数据源的物流、单据、支付和交付状态：承运人、eBL 平台、银行 / PSP、签发机构。

→
② 证明层 Proof
Verify source & rules

用 TEE 验证来源和业务规则，必要时以 ZKP 隐藏敏感字段；产出结构化签名声明。

→
③ 结算层 Settlement
Programmable escrow

由 Peer 式 Escrow 根据经验证的事件，释放、冻结或退回 USDC。

关键：三层各解决一件事，不能互相替代。数据上链之前，先要证明「这条记录确实来自那个可信源头，且绑定到这笔订单」。 Each layer solves one thing; none substitutes for the others.

03 · 必须区分的三种能力Three capabilities that are NOT the same

数据来源认证

Source authentication

验证记录确实来自船公司、银行或其他获认可的签发机构。

TEE 远程证明

TEE remote attestation

证明特定受保护环境运行了指定验证程序；不自动证明输入内容真实。

ZKP

Zero-knowledge proof

不公开完整业务数据，证明预设计算约束成立；本身不能证明现实货物或原始 API 记录真实。

因此第一版不一定要同时引入 TEE 和 ZKP。可以先使用 可信 API / 签名数据 + TEE 远程证明 + 结构化签名 + 链上验证，再对隐私与信任最敏感的场景加入 ZK 电路。 Start with signed data + TEE; add ZK circuits later where privacy demands it.

04 · 首要研究题目Primary research question

DCSA Track & Trace 2.2 → 可信数据源验证 / TEE → Peer-style USDC Escrow

P0 最小原型限定一个承运人、一个贸易线路、一个标准化物流事件、一条付款规则，先验证四个事实：

  1. 能否持续、合法地获取足够可信的事件数据？
  2. 如何证明 API 事件属于这笔订单而非另一笔订单？
  3. 该事件对买卖双方是否足以构成一个有商业意义的付款条件？
  4. 外部事件出现错误或回滚时，合约如何保护资金？

05 · 写在设计里的硬边界Hard boundaries, stated up front

「船公司记录已装船」不等于「箱内货物符合质量要求」。
单据内部一致不等于交易真实——若文件仅由卖家自行上传、没有可信签发者或原始系统校验，系统只能证明文件内部一致。
TEE 处理过 API 响应，不代表响应没有被伪造；TLS 终端认证、数据源签名、会话安全和输入来源证明必须纳入威胁模型。
Escrow 不是信用证的完整替代品；它默认不提供银行信用背书、融资、成熟的国际争议制度或法律执行网络。
